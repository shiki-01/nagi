# 計画: 英語の自動判定（日英混在入力）

状態: **計画のみ**（2026-10-23、ユーザー依頼「実装できそうか、まず計画だけ」）。実装は未着手。決定ログは `docs/decisions.md` H-47。

## 目的

ローマ字のまま英単語を打っても、日本語入力を切り替えずに英語として入力できるようにする。

- 例: `typescript` と打つ（ローマ字として読むと `tyぺsりpt` のような崩れた表示になる）→ `typescript` になる
- 例: `kyouhagoogledekensaku` → `今日はgoogleで検索`（日本語と英語が混ざった入力を切り分ける）
- 他のキーボードアプリで見られる「英語を打っていると判断して、自動で英語にする」機能に相当する

## 結論（実装できそうか）

**できる。** Nagi の構造と相性が良い。

- 入力を `Literal`（英数・記号。surface は変えないが推論の文脈には含める）として持つ仕組みがすでにある（`CLAUDE.md` の不変条件）。英語の区間は `Literal` のピースにすればよい
- ローマ字からかなへの変換は、キー列（raw）の「射影」にすぎない。raw を保持していれば、いつでも ASCII に戻せる
- 判定ロジックはコアに置く（フロントにロジックを持ち込まない）。macOS・iOS・Windows で共通になる

実装の規模は中〜大。判定の精度（日本語のローマ字と英単語が曖昧な入力）が主な難所。

## 方針

### 1. 判定に使う手がかり

| 手がかり | 内容 | データ |
| --- | --- | --- |
| ローマ字としての妥当性 | 全体をローマ字変換したとき、かなにならない ASCII が残るか（例: `typescript` → `ち`+`ぺ`+`s`+`く`+`り`+`pt`）。日本語に無い子音の連続（`pt`, `sc` など） | コア（既存の romaji） |
| 英単語の辞書 | raw（小文字）が英単語・識別子・技術用語の語彙にあるか。出現頻度つき | 取得データ（Mozc 辞書と同様に、同梱せず取得して SHA-256 検証） |
| 日本語としての尤もらしさ | 同じ raw を日本語として読んだときの辞書コスト（Viterbi）。日本語として十分に尤もらしければ英語にしない | コア（既存の辞書） |
| 文脈 | 直前の確定文字列（Surrounding Text）が ASCII か。アプリの種類（ターミナル・コードエディタは英語寄り）。直前が日本語か | 既存の `set_context` の `app_id` と文脈 |
| 学習 | 利用者が英語に直した・日本語に戻した語を覚える | 既存の学習（語単位の補正を追加） |

LLM（zenz）は日本語専用なので、判定の主役にはしない（将来、日本語として読んだときの尤度の比較に使う余地はある）。

### 2. 切り分け（日英混在）

raw のキー列に対して、日本語（ローマ字として読める区間）と英語（単語の区間）の分割を、格子（ラティス）上の最小コスト経路で求める。

- ノード: 区間 × 種別（日本語 / 英語）。日本語は既存の辞書の Viterbi のコスト、英語は語彙の頻度から作るコスト
- 経路のコストに、切り替えのペナルティ（日英の境界）を加える。強さの設定（下記）でペナルティを変える
- 出力は、日本語のピース（Japanese）と、英語のピース（`Literal`）の列
- 1 キーごとに全体を引き直すが、入力長は短い（チャンク分割あり）ので、`p95 < 16ms` の予算に収まる見込み。要計測

### 3. 見せ方（段階的に出す）

| 段階 | 内容 | リスク |
| --- | --- | --- |
| 段階 1 | Space の候補に、raw の ASCII を足す（判定の自信が一定以上のとき上位に）。**自動では変えない** | ほぼ無い。まずここで判定の精度を実機で確かめる |
| 段階 2 | 自信が高いとき、先頭の候補を ASCII にし、Enter でそのまま確定できる | 誤判定で日本語が英語になる |
| 段階 3 | 入力中に、かなにならない ASCII が残った時点で、表示を ASCII に切り替える（リアルタイム） | 切り替えの揺れ（ちらつき）。表示と確定の食い違い |

取り消し: 自動で英語にした直後に、もう一度同じ操作（F10 のような半角英数への切替、または専用のキー）で日本語に戻せる。戻した語は学習する（以後その語は日本語にする）。

### 4. 設定

- `[input.auto_english] mode`: `off` / `conservative`（慎重）/ `standard`（標準）/ `aggressive`（積極的）。既定は `conservative`（段階 1 のみ）
- アプリごとの上書き（ターミナル・コードエディタは `standard` 以上など）。`app_id` の判定は既存
- 例外語のリスト（常に日本語にする語・常に英語にする語）。ユーザー辞書の仕組みに載せる
- 次は変換しない: `/command`・`$skill`・`@file` のように記号で始まる語（コードやチャットの場面）

### 5. 難所と対策

- **曖昧な入力**: `sense`（せんせ/英語）、`text`、`term` のように、日本語のローマ字としても英単語としても読める。→ 日本語として尤もらしいときは日本語を優先。慎重な既定で始め、学習で補う
- **誤判定のコスト**: 日本語を打っているのに英語になるのは、逆より不快。→ 既定は自動で変えない（段階 1）。段階 2 以降は設定で
- **語彙データ**: 英単語の頻度つきリスト。ライセンスが緩いもの（SCOWL など）を第一候補にし、同梱せず取得する（`docs/ime-design-doc.md` §2.3 の方針）。技術用語（`typescript`, `kubernetes` など）は不足しがちなので、ユーザー辞書と学習で補う
- **モバイル**: iOS の拡張はメモリ上限が厳しい（約 177MB）。語彙は mmap できる形式（辞書と同様の fst）にする

### 6. 実装の順序（案）

1. raw のキー列を Composer のピースが保持していることの確認と、ローマ字の妥当性の特徴量（残る ASCII の割合など）。**評価用のコーパス**（日本語のローマ字入力と日英混在の文を数百件）を作る
2. 語彙データの取得（`nagi-datafetch`）と、mmap できる索引の組み立て
3. 判定（スコア）と、段階 1（Space の候補に ASCII を足す）。評価コーパスで、誤判定率と取りこぼし率を測る
4. 設定項目（`config/default.toml`、設定 GUI）とアプリごとの上書き
5. 段階 2・3、学習による補正

## 参考（他の実装）

調査した IME（Meltype、2026-10-23）は、同様の「日英の自動判定」を中核機能として持つ。判定の強さを 4 段階から選ばせ、英語にした語を学習し、コード系アプリでは英数を既定にする。**Meltype は GPL-3.0 なので、コードの転用はしない**（Nagi は MIT OR Apache-2.0）。機能の考え方を参考にするだけにとどめ、実装は仕様から独立して行う。
