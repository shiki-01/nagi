# 曖昧入力（タッチ誤差・タイポ許容）設計

- 版: v0.1 draft（2026-10-03）
- 位置付け: モバイルの主要な品質要素。設計書 §4.13 の「typo 耐性」（ローマ字再結合の緩和のみ）を拡張し、タッチ誤差・フリック誤判定・タイポをまとめて扱う
- 上位文書: `mobile-design.md`（§4.4 から本書を参照）、`mobile-roadmap.md`（D-7、M1/M2 の DoD）、`decisions.md` H-6（暫定判断・要レビュー）
- 状態: F-0（`nagi-fuzzy` のタイポ仮説生成）と D-2（プロトコル）は実装中。F-1 以降は未着手

## 1. 目的と範囲

小さな画面でのタッチ入力は誤入力が前提になる。誤入力を「入力の不確かさ」として扱い、変換候補側で救済する。

| 種別 | 例 | 主な発生場所 |
| --- | --- | --- |
| A. タッチ位置誤差 | `k` を狙って隣の `l` に触れる | QWERTY |
| B. フリック誤判定 | 「か」行の右フリック（く）が上フリック（け）に判定される | フリック |
| C. タイポ（打鍵の欠落・挿入・入れ替え） | `nihon` → `nihn`、`kanzi` → `kanizi`、`ta` → `at` | 全入力方式（デスクトップ含む） |
| D. かな水準の誤り | 濁点・小書きの付け忘れ（「かんこう」→「かんごう」） | 全入力方式 |

範囲外: 文脈に基づく文章校正（誤字訂正）、スペルチェック、クラウド補正。

D は優先度を下げ、v1 では A〜C を対象とする（D は §9 に拡張点のみ記す）。

## 2. 設計原則

1. **`reading` が真実という不変条件は変えない**。曖昧さは `Preedit`・`Segment` には持ち込まず、セッション内の入力側（Composer）に持つ。Segment.reading は常に「現在の第一仮説（打たれたとおり）」
2. **打った文字を黙って書き換えない**。補正は候補として提示し、ユーザーが選んだときに初めて reading を書き換える（標準 IME と挙動を揃える・入力を失わない）。自動適用は設定で明示的に有効にした場合のみ（§7）
3. **ロジックはコア、配列は知らない**。ユーザー定義の配列（並べ替え・カスタム）に対応するため、コアは特定レイアウトのジオメトリ・隣接表を持たない。フロントが描画しているレイアウトから「各キー（方向ゾーン）までの正規化距離」を計算して渡し、コアは距離を単純な関数でコストに換算し、辞書・ローマ字構造で絞り込む
4. **コストは入力品質に比例させる**。第一仮説の変換が良好なら追加の仮説は走らせない。`minimal` プロファイルでも動く（LLM 無し・辞書のみ）
5. **モバイルでビルドできる依存のみ**（追加依存なし。辞書の FST と標準ライブラリで完結させる）

## 3. 全体構成

```
key / touch代替 / flick代替（alternatives: text + distance）
        │
        ▼
 InputModel（nagi-fuzzy）  ──▶ 位置ごとの代替列 Vec<(char, logp)>   … Composer が保持
        │
        ▼
 HypothesisSearch（beam）  ──▶ 読み仮説 Vec<ReadingHypothesis{reading, cost}>
        │  辞書の前方一致で枝刈り（PrefixOracle）
        ▼
 Engine: 第一仮説で通常変換 → 品質が低い／曖昧のときのみ上位仮説も変換
        │
        ▼
 候補マージ（CandidateSource::Corrected）→ 候補バー
```

### 3.1 新 crate `core/fuzzy`（`nagi-fuzzy`）

- 依存: `nagi-romaji` のみ（辞書への依存は trait `PrefixOracle` で逆転させ、`dict` 側が実装する。engine が dict に依存しない既存の分離原則を保つ）
- `unsafe_code = "forbid"`、`missing_docs = "warn"` を継承
- 公開要素:

```rust
/// 入力 1 打鍵の候補分布（確率の高い順、最大 K 件）
pub struct KeyAlternatives { pub items: Vec<(char, f32 /* ln p */)> }

/// 読みの仮説。cost は入力モデル由来（小さいほど尤もらしい。第一仮説は 0）
pub struct ReadingHypothesis { pub reading: String, pub cost: f32, pub edits: EditSummary }

/// 辞書の接頭辞照会（枝刈り用）。読みが辞書の語の接頭辞になり得るか
pub trait PrefixOracle { fn has_prefix(&self, reading_prefix: &str) -> bool; }

pub struct FuzzyConfig { /* §7 */ }
pub struct KeyboardLayout { /* §4.1 */ }

pub fn expand(
    chars: &[KeyAlternatives],      // Composer が持つ位置ごとの代替
    table: &RomajiTable,
    oracle: &dyn PrefixOracle,
    cfg: &FuzzyConfig,
) -> Vec<ReadingHypothesis>
```

### 3.2 Composer への組み込み（`nagi-romaji`）

- `Composer` の `chars: Vec<(char, PieceKind)>` と並行して `alts: Vec<KeyAlternatives>` を保持する（添字を揃える）。物理キー・代替なしの入力では空（または要素 1 件）で、既存挙動・メモリ・速度に影響しない
- 挿入・削除・Backspace（G-49 の巻き戻し含む）・カーソル移動での編集は `chars` と `alts` を同時に更新する。`load_pieces`（`restore_session` 等）では `alts` を空とする（代替は復元しない。復元後は reading が第一仮説のみになる）
- 大文字・数字・Literal は代替を持たない（補正対象外）

## 4. 入力モデル

### 4.1 A: タッチ位置誤差（QWERTY・カスタム配列共通）

- **コアはレイアウトを持たない**。フロントはタップごとに、実際に採用したキー（第一候補）に加え、近傍のキーを `alternatives: [{text, distance}]` で送る。`distance` はタッチ位置からそのキーの中心までの距離を**キー幅で正規化**した値（0 = ちょうど中心）。キー幅が一様でない配列でも、フロントが描画上のキー矩形から計算する
- 送る範囲: `distance <= max_distance`（既定 1.0）の近傍キーのみ、最大 K 件（既定 3）。配列の並べ替え・カスタムはフロントの責務で、コアのコード・設定には影響しない
- コスト換算（単純な関数 1 つ）: `cost = 0.5 * (distance / sigma)^2`（`sigma` 既定 0.35。小さい方が尤もらしい）。第一候補（タップされたキー）は distance に関わらず基準のコスト 0 とし、他の代替との**差**として扱う（第一候補のキーが実際に最も近いとは限らないため、コアは代替の相対距離のみを使う）
- 親指のズレ（`touch_bias`）はフロントが座標補正として扱ってもよいが、v1 ではコア側で持たない（§9）
- 外付けキーボード・デスクトップの物理キー: 位置が無いので A は適用しない。C のみ

### 4.2 B: フリック誤判定

- フリックも同じ `alternatives` で表す。`text` は**ひらがな 1 文字**。フロントは、始点のキーと終点位置から、各方向ゾーン（中央・左・上・右・下）の中心までの正規化距離を計算し、近いものから送る（隣接する行のキーの方向ゾーンも `max_distance` 内なら含めてよい）。並べ替えた配列でも、フロントが描画しているゾーン配置から計算するだけで対応できる
- コスト換算は A と同じ関数。角度モデル（von Mises 等）は採らない（配列のカスタムに依存しない単純な距離に統一する）
- ローマ字を経由しないため、`insert_reading` の `reading`（第一候補）+ `alternatives` として渡す（D-2）。Composer には `PieceKind::Kana` として入る

### 4.3 C: タイポ（編集操作）

ローマ字入力列（打たれたキー列）に対し、編集距離を限定して仮説を作る。キーボード配列（隣接）には依存せず、ローマ字の**構造**（子音・母音）と日本語ローマ字で取り違えやすい**音の紛れ**に基づく。

| 操作 | 内容 | 既定コスト（nat） |
| --- | --- | --- |
| 入れ替え | 隣接 2 打鍵の転置（`at` ↔ `ta`、`hsi` → `shi`） | 2.0 |
| 子音の紛れ | `l`↔`r`、`c`↔`k`/`s`、`b`↔`v`、`j`↔`z` など音の類似による置換。小さな定数表（`CONSONANT_CONFUSIONS`）。設定で無効化可能 | 2.5 |
| 欠落補完 | 子音の後の母音欠落・子音の欠落を 1 文字補う（`nihn` → `nihon`）。補う文字はローマ字テーブルから「入れると合法な連続になる文字」を導出し、辞書の枝刈りで絞る | 3.0 |
| 余剰削除 | 1 打鍵を削除（`kanizi` → `kanzi`。二重打鍵 `kk` の誤りを含む） | 3.0 |

- 隣接キー置換（QWERTY 隣接表）は採らない。タッチ・物理キーの位置ずれは A（距離）が担う。物理キーの隣接ミスは当面扱わない（必要なら F-5 以降で実データを見て検討）
- 上限: `max_edits`（既定 1。入力が 6 打鍵以上なら 2）。仮説全体の `cost` 上限 `max_cost`（既定 6.0）
- 適用範囲: **カーソル位置から後ろ `window` 打鍵（既定 8）** のみ。全位置に適用すると組合せが増え、レイテンシ目標（p95 < 16ms）を満たせない
- ローマ字として不正な組合せ（テーブルに接頭辞が無い）は変換器側で素通し（Raw）になるため、仮説生成では変換器を実際に走らせて合法な読みだけを採用する

## 5. 仮説探索

ビーム探索で、位置ごとの代替と編集操作をまとめて展開する。

- 状態: `(入力位置 i, 変換器の保留状態, これまでの読み, cost, 編集数)`
- 遷移: 位置 i の代替（各 `-ln p` をコストに加算）、または編集操作（上表）
- ビーム幅 `beam`（既定 8、`minimal` は 4）。位置ごとに cost 順で上位に絞る
- **辞書による枝刈り**: 状態ごとに「辞書の語として分割可能な境界位置の集合」を持つ（位置 0 は境界。確定ひらがな列の位置 p は、境界 q（p から 10 文字以内）で `contains_word(reading[q..p])` が成り立てば境界）。生存条件は、最後の境界 q から末尾までの未確定部分が空、または `has_prefix(reading[q..])`。補正仮説の最終採用条件は「末尾が境界（全体が辞書語に分割可能）」で、`unknown_budget` > 0 なら未知語として許す連続文字数の上限とする。**第一仮説は枝刈り・コスト上限の対象外**（辞書にない固有名詞・外来語でも残す）。`PrefixOracle` は `has_prefix` と `contains_word` の 2 メソッド（FST のみ使用）
- 出力: cost 昇順の `ReadingHypothesis`（重複は cost の小さい方を残す）。第一仮説（代替の第 1 位だけを選んだ読み = 打たれたとおり）は必ず含め、cost は 0 とする
- 計算量の目安: 窓 8 × 代替 3 × ビーム 8 ≒ 数百状態。romaji 変換と FST 照会が主で、目標は p95 +3ms 以内（§8 で実測）

## 6. 変換との統合

### 6.1 いつ追加仮説を走らせるか

打鍵ごとには走らせない（ひらがな反映の p95 < 16ms を守る）。次のタイミングのみ:

- **Space 変換**（Converting への遷移時）と**候補バーの更新（デバウンス後）**
- ライブ変換のデバウンス満了時（既存の `live_convert`）。ただしライブ変換の**表示は第一仮説のまま**とし、補正はしない（§2-2）

走らせる条件（いずれかを満たすとき）:

1. 第一仮説の変換結果が低品質: 辞書のみ経路では「全文が未知語／ひらがなフォールバック」の割合が閾値以上、LLM 経路では `score` が閾値未満
2. 入力モデル上の曖昧さが大きい: 第 2 仮説の cost が `ambiguity_margin`（既定 1.5 nat）以内
3. 仮説の読みが辞書の語としてのみ成立（第一仮説は辞書に前方一致しない文節を含む）

上記を満たさなければ追加仮説は計算しない（通常入力では実質ゼロコスト）。

### 6.2 バックエンドの拡張

`ConversionBackend`（`engine/src/backend.rs`）に既定実装付きのメソッドを追加する（既存実装を壊さない）:

```rust
/// 読みの仮説ごとの文全体変換。結果は変換スコアと入力 cost を合成した順位で返す。
/// 既定実装は第一仮説のみを `convert_sentence` で変換する（曖昧入力に非対応のバックエンドは従来どおり）
fn convert_hypotheses(
    &self, hyps: &[ReadingHypothesis], left_context: &str, limit: usize,
) -> Vec<ScoredSentence> { ... }
```

- `BackendCandidate` には現在スコアが無いので、`ScoredSentence { segments, conv_cost, hypothesis_index }` を新設する（`BackendCandidate` の形は変えない）
- 順位の合成: `total = conv_cost + λ · input_cost`。λ は `fuzzy.input_weight`（既定 1.0）。dict の語コストと LLM の対数確率は尺度が違うため、**辞書経路・LLM 経路それぞれで λ を較正する**（§8 の評価で決める）
- LLM 経路: 追加仮説は `ConversionModel::score` による再採点で処理する（仮説ごとにビームサーチ全体を回さない）。プロファイル別の上限: `quality` 3 仮説・`balanced` 2・`light`/`minimal` 辞書のみで 3（LLM 不使用）

### 6.3 候補への反映

- 補正由来の候補は `CandidateSource::Corrected`（enum に追加。プロトコル・typeshare・Swift 型の更新あり）。アイコン・注記（「◯◯と入力？」）はフロントが割り当てる
- 順位: 第一仮説の最良候補を先頭に置く。ただし第一仮説の変換が条件 1 に該当する（ほぼ未知語）場合は、補正候補の最良を先頭にしてよい（既定: 先頭にはしない。`fuzzy.promote_corrected = false`）
- 補正候補を選択すると、その文節の `reading` を仮説の読みに書き換える（`Action::SelectCandidate` の拡張。Segment の `reading` と `surface` の整合はアライメントで保つ）。取り消し（Undo）は選択前の reading に戻せるよう、元の reading を保持する（`Styled` セグメントの Undo と同じ方式）
- 候補バーでの表示件数・順位は D-6（予測候補仕様）と合わせて決める

## 7. 設定（`config.toml` の `[fuzzy]`）

| キー | 既定 | 内容 |
| --- | --- | --- |
| `enabled` | プロファイルによる（モバイルは true、デスクトップは false → 実機評価後に再検討） | 曖昧入力全体の ON/OFF |
| `touch_sigma` | 0.35 | タッチ位置誤差の標準偏差（キー幅比） |
| `max_edits` | 1 | タイポ補完の最大編集数 |
| `window` | 8 | 補正を適用する直近打鍵数 |
| `hypotheses` | 3 | 変換に回す仮説の最大数（プロファイルで上書き） |
| `input_weight` | 1.0 | 入力 cost の重み（λ） |
| `ambiguity_margin` | 1.5 | 追加仮説を走らせる曖昧さの閾値 |
| `auto_apply` | `off`（`off` / `conservative`） | 自動で reading を書き換える（§2-2。`conservative` は第一仮説が全て未知語かつ補正候補の total が第 1 仮説より大幅に良いときのみ） |
| `promote_corrected` | false | 補正候補を先頭に出す |

- 全項目を `config/default.toml` に日本語コメント付きで追加し、`definitions()` に GUI 用の `SettingDef` を追加する（G-41 のスキーマ駆動）
- プロファイル: `minimal` は A・B のみ（C の編集操作は `max_edits = 0`）で `hypotheses = 3`。`light`/`balanced`/`quality` は C を有効にする

## 8. プロトコル変更（D-2 と同時に実施）

D-2（`insert_reading` / `perform_action`）に含めて**同時に**入れる（破壊的変更を 2 回に分けないため）。

- 共通型 `InputAlternative { text: String, distance: f32 }`（`text` は 1 文字。`distance` は §4.1 の正規化距離）
- `insert_reading { session_id, reading, alternatives? }`: ローマ字を経由しない挿入（フリック・12キー・かな入力）。`alternatives` はフリックの代替ひらがな
- `process_key` に任意フィールド `alternatives?` を追加（QWERTY のタッチ。省略時は位置情報なし。既存クライアントと互換）
- レイアウト ID・座標・方向の角度はプロトコルに載せない（カスタム配列に依存させないため）
- 応答の候補に `CandidateSource::Corrected` を追加する（F-1。任意の `note`: 補正前後を示す短い文字列。入力内容を含むためログには出さない）
- 学習・secure input: 補正の学習（§9）は secure input／シークレットモードでは無効。タッチ距離はログに出さない（既存のログ方針どおり）
- D-2 の時点では、`alternatives` はプロトコルとエンジンの入口で受け取り検証するだけで、挙動には使わない（Composer への保持は F-1）

## 9. 学習（個人適応）

- 補正候補を選択 → 「入力した読み → 選んだ読み」の対を学習ファイルに記録（スキーマバージョンを上げる。既存の TSV に新しい種別行を追加）
- 用途: (1) 同じ対が繰り返し選ばれたら、`input_weight` を下げた（優先的に出す）仮説として扱う。(2) タッチの系統的ズレ `touch_bias` を、確定した読みと元の座標の差から指数移動平均で更新する（QWERTY の左右の手別に保持しない。1 つの bias のみ。v1）
- 補正が選ばれず第一仮説が確定されたとき: bias は更新しない（誤学習を避ける）
- 削除: 「学習データをワンコマンドで全削除」の対象に含める
- D（かな水準の誤り）の拡張点: 同じ `KeyAlternatives` の枠組みで、濁点・小書きの代替をかな 1 文字の代替として追加できる（`ReadingHypothesis` の生成側のみの変更）。v1 では実装しない

## 10. テスト・評価

1. **単体**: `nagi-fuzzy` の入力モデル（既知の座標 → 期待する上位キー）、編集操作（`nihn`→`nihon` 等の表）、枝刈り、`max_edits`/`window` の境界
2. **状態機械ゴールデン**: 代替付きの入力列 → 第一仮説の reading が変わらないこと（§2-2 の回帰）、Backspace・カーソル編集で `alts` が `chars` とずれないこと（G-49 の巻き戻し含む）
3. **精度評価（合成ノイズ）**: Mozc の `evaluation.tsv`（`cargo xtask fetch-dict`）の読みから、ガウス誤差でキー位置を摂動した打鍵列と、編集操作でタイポを混入した打鍵列を生成し、`nagi-eval` の新モード（`--noise touch|typo`、ノイズ率指定）で次を計測する: 補正なし／あり の top-1・top-5 正解率、第一仮説が正しい入力での劣化（**劣化 0 が条件**。`nagi-eval` の `--no-llm` 経路で既存の精度が変わらないこと）
4. **レイテンシ**: キー入力 → ひらがな反映 p95 < 16ms（追加 +3ms 以内）、Space 変換 → 候補表示 p95 < 150ms（追加 +20ms 以内）。`nagi-eval` のレイテンシ計測にノイズ条件を追加
5. **実機（M0/M1）**: 実際のタッチログ（ユーザー本人の入力。収集は明示的に開始し、座標と確定結果のみ・ローカル保存）で σ・bias・コスト表を較正する。合成ノイズの結果は参考値で、較正は実測を正とする

| F-0 | `nagi-fuzzy` 骨格 + C（タイポ）のローマ字水準の仮説生成 + `PrefixOracle`（dict 実装）+ 単体テスト | D-1（mmap 化）は不要 | 既存精度が不変、`nihn` 等で補正候補が出る（デスクトップでも有効にできる） |
| F-1 | Composer の `alts` 保持 + `convert_hypotheses` + `CandidateSource::Corrected` + `[fuzzy]` 設定 + ゴールデンテスト | F-0 | Space 変換で補正候補が候補に並ぶ。第一仮説の挙動は不変 |
| F-2 | A（タッチ）: 距離 → コスト換算 + Composer の `alts` へ接続（プロトコルの `alternatives` は D-2 で追加済み） + 合成ノイズ評価（フロントの距離計算を模す） | F-1、D-2 | 合成ノイズで top-5 が改善し、劣化 0 |
| F-3 | B（フリック）: `insert_reading` の `alternatives`（ひらがな代替）の接続 | F-2 | 同上（フリック版の合成ノイズ） |
| F-4 | 学習（`touch_bias`・補正選択の記録） | F-2 | 実機ログで bias が収束する |
| F-5 | 実機較正（σ・コスト表・λ） | M1 の実機 | `decisions.md` に較正値を記録 |

F-0〜F-1 はデスクトップ単体でも価値があり、モバイル着手前（D 系と並行）に進められる。F-2〜F-3 は M1（Android MVP の QWERTY）・M2（フリック）の DoD に含める。

## 12. リスクと未決事項

| 項目 | 内容 | 対策 |
| --- | --- | --- |
| 誤補正の不快さ | 正しい入力を補正候補が邪魔する | §2-2（書き換えない）、§6.1（条件を満たす時のみ）、第一仮説の劣化 0 を評価の条件にする |
| レイテンシ | ビーム探索・仮説変換のコスト | 打鍵ごとに走らせない（§6.1）。窓・ビーム・仮説数の上限をプロファイルで制御 |
| 辞書にない語（固有名詞・外来語）の枝刈り誤り | 正しい入力から仮説を捨てる | 第一仮説は枝刈りしない（必ず残す）。枝刈りは補正仮説にのみ適用 |
| コスト表・σ・λ の妥当性 | 暫定値で実機に合わない | F-5 で実測から較正。設定で調整可能にしておく |
| iOS 拡張のメモリ | 仮説の保持・探索 | 状態数に上限（ビーム幅 × 窓）を置く。M0 のメモリ実測に含める |
| 未決: デスクトップでの既定 | 物理キーで C を既定 ON にするか | F-1 完了後に実機で評価して決める（暫定 OFF） |
| 未決: `touch_bias` を手別に持つか | 左右の親指で別 | F-4 の実機ログで判断 |
