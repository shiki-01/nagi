## A. アプリの種類ごとの既定モード・素通し

状態: **実装済み**（2026-10-23。コア・設定・設定 GUI。決定は `docs/decisions.md` H-49。フロントは未変更で、macOS の `adoptSelectedMode` との相互作用は実機で要確認）

### 目的

ターミナル・コードエディタ・AI エージェントのチャットなど、英数が主な場面で、毎回モードを切り替えなくて済むようにする。

### 仕様

- **アプリの分類**: `set_context` の `app_id`（macOS の bundle id、Windows の実行ファイル名）を、設定の分類表で `code`（コードエディタ・ターミナル）／`chat`／`general` に分ける。既定の表を同梱し（例: `com.apple.Terminal`、`com.googlecode.iterm2`、`com.microsoft.VSCode`、`com.jetbrains.*`、`com.apple.dt.Xcode` を `code` に）、利用者が上書き・追加できる
- **既定モード**: アプリの分類ごとに、フォーカスを得たとき（`focus_in`）の入力モード（ひらがな / 英数 / 前回のまま）を設定する。既定は `code` を「英数」、それ以外は「前回のまま」
- **素通し**: 未入力の状態で、先頭の文字が `/`・`$`・`@`・`!`・`:`・`#` のとき、その語の入力中は日本語変換せずに ASCII のまま入力し、確定する（スラッシュコマンド・シェル・メンション・ファイルパスの入力）。設定で有効・無効と記号の一覧を変えられる
- **モードの記憶**: アプリごとに、利用者が手で切り替えたモードを覚える（次回そのアプリでその状態で始まる）。設定でオフにできる
- 状態機械には、`Action::SetMode` を `focus_in` の応答で出すだけでよい（新しい Action は不要）。素通しは、Composer の先頭文字の判定（Direct 状態）と、`Literal` のピースの扱いの小さな追加

### 実装の足場

`app_id` は既に送っている（macOS: `NagiInputController.swift`、iOS・Windows も対応）。コアの設定（`core/config`）に分類表とモードの設定を追加し、`engine.rs` の `focus_in` と、未入力時のキー解決（`keymap.rs` の Direct）を拡張する。設定 GUI はコアの記述子に項目を足すだけで出る。

### テスト

ゴールデン（`focus_in` で app_id を与えたときのモード、素通しのキー列）、設定の読み込み、既定の分類表。

## B. 他の IME のユーザー辞書の取り込み

状態: **実装済み**（2026-10-23。`core/dict/src/import.rs`・JSON-RPC `import_user_dict`・macOS 設定ウィンドウの「取り込み…」。決定は `docs/decisions.md` H-50。各 IME の実物での確認と Swift のコンパイルは未了）

### 目的

乗り換えのときに、単語登録を移せるようにする。

### 仕様

- 取り込める形式（独立に仕様化した、各 IME の公開されているエクスポート形式）:
  - Mozc / Google 日本語入力: TSV（`読み<TAB>単語<TAB>品詞<TAB>コメント`）— すでにユーザー辞書の正の形式
  - Microsoft IME: テキスト形式（UTF-16。`読み<TAB>単語<TAB>品詞`、先頭に `!Microsoft IME Dictionary Tool` の行）
  - ATOK: テキスト形式（`読み<TAB>単語<TAB>品詞`。形式の差（`!!ATOK_TANGO_TEXT_HEADER_1` の行）を吸収）
  - macOS 標準のユーザ辞書: プロパティリスト（`phrase` と `shortcut` のキーを持つ配列。「ユーザ辞書」から書き出したもの）
  - 単純な「読み<TAB>単語」の 2 列のテキスト
- 各形式の詳細（ヘッダー行・文字コード・品詞の名前）は、記憶に基づく部分があるので、実装時に各 IME の書き出しの実物で確認する
- 取り込みは Mozc TSV への変換として実装する（正の形式は変えない）。品詞は、Nagi の辞書の品詞に写せるもの（名詞・人名・地名・固有名詞・動詞・形容詞など）は写し、写せないものは「名詞」にする
- 取り込み後に、件数と、スキップした行の件数と理由（読みが不正、重複など）を表示する。**重複は既存を優先**
- 呼び出し: 設定ウィンドウの「ユーザー辞書」から（macOS は「ユーザ辞書を編集…」の隣に「取り込み…」を足す）。コアに `import_user_dict`（ファイルの内容と形式の自動判定）を JSON-RPC に足す。形式の判定はファイルの先頭の行と構造から

### 実装の足場

`core/dict`・`core/server` のユーザー辞書（Mozc TSV 互換）の読み込みの前段に、変換器（`core/dict/src/import.rs`）を足す。JSON-RPC は加算的な追加。

### テスト

各形式の小さなサンプル（自作）で、変換結果・スキップ・文字コード（UTF-16 / UTF-8、BOM）を検証する。

## C. 英語の綴りの「もしかして」

状態: **実装済み**（2026-10-27。コア。決定・重み・実測は `docs/decisions.md` H-70。実機確認は残る）

Nagi にはすでに、キーの近接による入力ミスの補正候補「もしかして」（`CandidateSource::Fuzzy`。`docs/decisions.md` の曖昧入力の項）がある。これを、日英の自動判定（`docs/plan-auto-english.md`）の英語の語に広げる。

- 英語の語彙（自動判定で取得するデータ）に対して、編集距離 1〜2 とキー近接の重みで、綴りの候補を出す（例: `typscript` → `typescript`）
- 候補は Space の変換候補の中に、出所「もしかして」で出す（既存の仕組み）
- 自動判定の段階 1（候補に出すだけ）の後に入れる

## 1. 記号の変換・形式候補・電卓

状態: **実装済み**（2026-10-23 着手。H-55・H-60。実機確認は残る）。内容:
- 電卓: 既定を有効にし、`1+2=`・全角・複数項の式に対応
- 数字・記号だけの入力（`Literal`）でも、Space で候補（電卓・全角/半角・記号など）を出す
- 記号の変換: `かっこ` や `(` などから、装飾されたかっこ・記号の候補
- 変換候補の末尾に、ひらがな・カタカナ・全角英数・半角英数を並べる（通常の IME と同様）

## 取り入れない点

- キーボードを直接監視して文字を送る方式（入力を失うおそれ。TSF / IMKit を使う Nagi の設計とも合わない）
- Microsoft IME の変換エンジンへの依存（ローカル完結・移植性の方針に合わない）
- 管理者権限なしで動かす変換ボックス方式（TSF が前提の現設計と別経路になる。Windows の導入の障壁は、`docs/windows-install.md` の方針で対応する）
