# iOS 実機での確認事項

実機でしか確認できない項目。実装側は確認済みにできないため、ビルドを入れたタイミングでまとめて確認する。
結果は各項目に追記し、問題があれば `docs/decisions.md` に経緯を残す。

## 0. 要判断（ユーザーが決める事項）

**すべて決定済み**（`docs/decisions.md` H-22）。実機での確認が残る点を併記する。

- **(a) 診断ログの既定**: **決定済み**。TestFlight 期間中は既定 ON・入力内容を含む（パスワード欄は伏せる）。App Store 配布版は既定 OFF・内容を含めない。`CLAUDE.md` に「テスト配布期間のみの例外」として明記した（§3 の D-1）
- **(b) `RequestsOpenAccess`**: **`true`**（H-18。`false` ではフルアクセスのトグルが設定アプリに出ず、セットアップ状況が未検出のままになったため）。App Store 審査では用途の説明が必要
- **(c) iOS の既定モデル**: **決定済み: small。ただし端末の予算で自動選択**（`NagiModelRecommendation`。`予算 − (モデルサイズ + 20MB) ≥ 40MB` を満たす最大のモデル。Picker で明示選択すればそれを優先）。実機（拡張の上限約 177MB）で small が選ばれることをホームのデータ欄「推奨: small（…）」で確認する。small では同期の待ち 30ms を超えた結果が約 0.6 秒後に差し替わる（H-10）ので、候補のちらつきが気にならないかも見る

  - URL スキーム: Safari で `nagi://layout?data=<base64url>` を開く → アプリが起動して取り込み結果のアラートが出る（不正な data ではエラー文）

- [確認済み 2026-10-22・問題なし] ユーザー辞書の画面（`App/UserDictionaryView.swift` `Shared/UserDictStore.swift`。ホーム >「ユーザー辞書・スニペット」）:

  - プライバシー表示: About のプライバシー欄が、TestFlight ビルドでは「診断ログを端末内に記録・既定で有効・入力文字を含みうる・入力テストの記録スイッチで無効化できる」と出る。候補バー右端の「検証」ボタンと Probe 画面の「結果を入力欄に挿入」が、TestFlight / 開発用ビルドでだけ出る（App Store 配布のビルドでは出ない。App Store 提出前の TestFlight ビルドでは出ることのみ確認できる）
  - 学習データ削除（コアに繋がらない経路）: `learning.tsv` と `learning-next.tsv` の両方が消える（次語予測の記録も復活しない）
  - `config.toml` の自動生成: ユーザー辞書の画面を開いても `config.toml` の更新時刻が変わらない（内容が同じなら書き直さない）。読めない状態の `config.toml` を上書きしない
  - ユーザー辞書: 単語・読みが 256 文字を超えるとエラー。`user_dict/` を読めない状態では登録・削除ができず、エラーが出る（空で上書きしない）。数千件の取り込み中も画面が固まらない。大きさを取れないファイルは取り込めない

### 5.2 メモリ閾値（150 / 1024 / 2048MB）と LLM の再読み込み（H-16・H-26）: 報告待ち

**起きたときのログの見方:** 次の行を時刻の順に探す。
1. `memory warning footprint=… available=…`
2. `set_environment (memory warning) … memory=critical`
3. `llm released by core (get_status llm=false)`
4. `set_environment (focusIn …)` または `set_environment (…) … memory=normal`
5. `reload_model ok=true`
6. `llm restored`

- **期待:** 警告の直後も入力が止まらず、入力中の文字は残る。候補バーに「簡易モード（辞書のみ）」の注意が出る。約 10〜12 秒で LLM が戻り（1 と 6 の時刻差）、注意が消え、候補が LLM 付きに戻る。
- **NG のとき報告すること:** `llm still active after memory_pressure=critical` が出た（コアが LLM を解放しなかった）。`restart core` が出た。注意が消えない、または 30 秒以上戻らない。強制終了された（ログは残らないことがあるので、時刻と操作を書く）。
- **閾値 150MB の見直し:** 上限が 150MB 前後の端末の実測（§5.4）と合わせて決める。

### 5.3 フルアクセス（触覚）の OFF / ON の比較（H-18）: 据え置き（未確認）

**内容:** フルアクセスを OFF にしたとき、触覚（振動）が出るかを確かめる。出なければ、「触覚にはフルアクセスが要る」と案内を出す必要がある。

1. 設定 アプリ → 一般 → キーボード → キーボード → Nagi を開く。「フルアクセスを許可」を **OFF** にする。
2. Nagi アプリの「設定」タブで「キー入力の触覚」を「強」にする。「触覚の方式（互換モード）」は「標準」のままにする。
3. 「入力テスト」タブ（またはメモ）でキーを 10 回ほど押す。振動するかを記録する（しなくても、その結果を報告する）。
4. 設定 アプリで「フルアクセスを許可」を **ON** にして、同じように 10 回押す。期待は振動すること。
5. 「触覚の方式（互換モード）」を「互換」にして、OFF と ON の両方で同じように押す。互換モードが、フルアクセスの有無にかかわらず振動するかを記録する。

**診断ログの行:** `feedback prepare haptic=… engine=… sound=… fullAccess=… generator=…`（`fullAccess=` が OFF / ON を示す）、`haptic fire kind=… engine=standard fullAccess=… generator=…`、`haptic fire kind=… engine=compat fullAccess=… generator=none requested=true`（互換の場合）。

**NG のとき報告すること:**
- OFF で振動しない → 「触覚にはフルアクセスが要る」という案内をアプリ内に出すかどうかは、ユーザーの判断。
- OFF でも振動する → 「フルアクセスが要る」は触覚については不要になる。その旨を報告する。
- どちらでも振動しない、または ON でも振動しない → 設定の値とログを送る。

**選択肢:** 案A（標準モードの OFF / ON 比較。仕様の判断に直結し、手間は小）、案B（互換モードでも比較。互換が OFF でも振動すれば標準の問題を避けられる）、案C（クリック音など他の機能と一緒に確認する）。

### 5.4 他機種での拡張のメモリ上限と応答時間（H-17・H-22(c)）: 後日（ユーザーが実施予定）

**内容:** 今の実測は iPhone 16e（RAM 8GB）だけ。上限は機種ごとに違う可能性がある。

1. 別の iPhone に同じ TestFlight ビルドを入れる（TestFlight の招待を送る）。
2. その端末の Nagi アプリで次の値を書きとめる: 「ホーム」→「メモリ」欄の「上限の推定」の数字、「ホーム」→「データ」欄の「推奨: …」（small・xsmall・推奨なし のどれか）、機種名と iOS のバージョン（設定 → 一般 → 情報）。
3. 「入力テスト」タブで文章を 10 文ほど入力し、候補がどれくらいの速さで出るかを見る（体感で良い）。
4. 余裕があれば、「About」タブ →「開発者向け」→ Probes の「llm_load_light」を実行し、結果の画面をコピーして送る。

**期待:** 上限が 150MB 以上の端末では推奨が small か xsmall になる。どちらも載らないときは「推奨なし」と日本語で出る。変換が止まらない。

**NG のとき報告すること:** キーボードが勝手に消える、または再表示で入力中の文字が消えた（機種名、iOS のバージョン、時刻、操作）。上限の推定が 150MB より小さい（その数字と推奨の文字）。

### 5.5 既定の `sync_budget_ms`（同期の待ち時間）の決定（H-10）: 未決

**内容:** 変換の候補を待つ時間。現在の既定は `Shared/ProductSession.swift` の `syncBudgetMs = 30`。待ちが短いほど速く候補が出るが、LLM の結果が後から差し替わる。設定の「詳細」の「変換の同期待ち時間（`conversion.sync_budget_ms`）」で値は変えられる。ただし数値を測る Probe は 30ms に固定されているため、別の値の数値を測るには開発側で Probe を変える必要がある。

**A. 体感で確かめる（すぐできる）:** 「入力テスト」タブで文を 10 文ほど入力して Space で変換する。候補が遅れなく出るか、後から別の候補に差し替わるとき（ちらつき）、文字が大きく動いたり入力中の文字が消えたりしないかを見る。設定の同期待ち時間を変えたら、キーボードを開き直して同じ見方で比べる。

**B. Probe で数値を取る（開発者の作業が要る）:** 「About」→「開発者向け」→ Probes →「llm_load_light」を実行し、「Space 応答 p50 / p95」、`tail_space_ms`（入力を止めた後の変換にかかった時間）、`tail_async_arrival_ms`（後から LLM の結果が届くまでの時間。-1 は届かなかった）を書きとめる。結果の画面をコピーして送る。

**判断基準（案。ユーザーが決める）:**
- 案A（30ms・現状）: 候補は即時に出る。LLM の結果は約 0.6 秒後に差し替わる（small の場合。H-10）。
- 案B（80ms 程度）: 差し替えが減るかもしれないが、数値は未測定。
- 案C（150ms）: 目標の「Space 変換→候補表示 p95 150ms」ぎりぎり。
- 基準の案: 「Space 応答の p95 が 50ms 以下」かつ「差し替えの時間が 1 秒以内」を満たし、かつ差し替えが気にならない（ユーザーの体感）最小の値を選ぶ。

**選択肢:** 案A（体感で決める。手間は小だが数値は出ない）、案B（Probe で数値を取る。Probe の待ち時間を選べるように開発側の変更が要る）、案C（差し替わった回数を診断ログで数える。差し替えの記録がログに出るかは未確認。開発側で確認が要る）。
