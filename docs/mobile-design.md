# Nagi モバイル版（iOS / Android）設計メモ

- 版: v0.2 draft（2026-09-29。配布・更新・azooKey 参考の方針を反映）
- 位置付け: 実装は未着手。**デスクトップ版の開発中から守るべき制約**（§3）を定め、モバイル対応時にコアの作り直しが発生しないようにするための文書
- 上位文書: `ime-design-doc.md`（全体設計）、`decisions.md` H 節（本件の決定・未決事項）
- 記述の確度: OS の制約値（メモリ上限等）は公式に明示されていないものを含む。「要検証」の項目は Phase M0（§7）で実測して確定する

## 1. 目的と範囲

- iOS / Android でも Nagi のコアエンジン（状態機械・IR・辞書 + Viterbi・LLM 推論・学習）をそのまま使う
- 差別化点（セグメント IR・範囲操作・スタイル変換）はモバイルでも維持する。操作手段はキーではなくタッチ UI になる
- デスクトップ版の v1（Phase 1〜6）より後に着手する。着手までの間は §3 の制約を守ることだけを求める

範囲外（モバイル版 v1 でもやらない）:
- クラウド変換（全体方針どおりローカル完結）
- 手書き・音声入力
- タブレット専用レイアウト（スマホのレイアウトを拡大して使う）

## 2. デスクトップとの差分（前提となる OS 制約）

| 項目 | デスクトップ | iOS（Custom Keyboard Extension） | Android（InputMethodService） |
| --- | --- | --- | --- |
| コアの実行形態 | フロントの子プロセス（stdin/stdout） | **子プロセス生成不可**。拡張プロセス内でライブラリとして動かす | IME アプリのプロセス内でライブラリ（JNI）として動かす。`android:process` で UI と分離も可 |
| メモリ | 数百 MB〜 | **拡張のメモリ上限が厳しい**（公式値なし。数十 MB 級との報告が多い。要検証） | 端末依存だが iOS より緩い |
| 入力イベント | 物理キー（keysym） | タッチ（自前キーボード UI）。外付けキーボードは拡張に届かない | タッチ（自前 UI）+ 物理キー（`KeyEvent` が届く） |
| preedit 表示 | OS の marked text + 属性 | `setMarkedText`（属性・下線の指定不可） | `setComposingText`（Span で装飾可） |
| 候補表示 | 独自ウィンドウ | キーボード上部の候補バー | キーボード上部の候補バー |
| データ（辞書・モデル） | ユーザー領域に取得 | 本体アプリが取得し App Group 共有コンテナ経由で参照。**拡張からの参照には「フルアクセス」許可が必要** | アプリ専用領域に取得 |
| パスワード欄 | secure input 検知で学習停止 | OS がシステムキーボードへ強制切替（Nagi は呼ばれない） | `EditorInfo.inputType` のパスワード種別・`IME_FLAG_NO_PERSONALIZED_LEARNING` で学習停止 |
| 配布 | ad-hoc 署名 + スクリプト | SideStore によるサイドロード（§6） | APK 直接配布（§6） |
| アップデート | 自前確認 + ed25519 検証 | 本体アプリで確認。データは直接更新、アプリ本体は SideStore 経由で上書き（§6.3） | 本体アプリで確認・APK を取得して上書きインストール（§6.3） |

## 3. デスクトップ開発中から守る制約（今から適用）

以下は Phase 1〜6 の実装・レビュー時点で守る。違反すると後からコアの改修が必要になるもの。

1. **コアはライブラリとして完結させる**
   - 変換ロジックを `server` のバイナリ側（`main.rs`・stdio ループ）に置かない。`Server::handle_line`（行入力 → 行出力）が既にトランスポート非依存なので、この境界を維持する
   - 非同期通知（`update_preedit` 等）も「出力行を渡すコールバック / チャネル」経由で出し、stdout への直接書き込みに依存しない
   - `std::process`（子プロセス生成・`exit`）をコアのライブラリ経路で使わない（PID 取得による一時ファイル名は可）
2. **パスとプラットフォーム情報は外から注入する**
   - データ・設定・学習ファイルのパスは引数で受け取る（既存の `--data-dir` / `--user-dir` 方式を維持）。OS 標準ディレクトリの推測はバイナリ側で行う
   - 環境プロファイルの判定材料（メモリ量・電源・温度）は、コアが OS API を直接叩くのではなく `initialize` の capability / 通知でフロントから渡せる形にする。デスクトップではサーバー側の既定実装で埋めてよい
3. **メモリ使用量を意識した辞書・モデル形式**
   - 現状の辞書は全量をヒープに読み込む（`Dictionary::load` → `fs::read`）。モバイルでは mmap で読める形式（ゼロコピー参照）への移行が必要になる見込み。辞書形式を変更する機会があれば mmap 可能な配置を優先する
   - LLM はモバイルでは任意機能とし、`minimal`（辞書 + Viterbi のみ）で常用に耐える品質を維持する
4. **アップデート確認・署名検証をライブラリから呼べるようにする**
   - モバイルでも更新確認を行う（§6.3）。現状の更新確認・ed25519 検証（`server/src/update_check.rs`）は `imserver` から切り離して、本体アプリ（FFI 経由）からも呼べる形を保つ
   - 更新対象を「アプリ本体」と「データ資産（辞書・モデル・プリセット）」に分け、データ資産はアプリの再インストールなしで差し替えられるようにする（マニフェストでバージョンと SHA-256・署名を管理）
   - キャリブレーション推論は時間・電力の上限を設ける
5. **キー以外の入力経路を塞がない**
   - IR は reading（ひらがな）が正なので、ローマ字を経由しない「かなの直接挿入」（フリック入力）を後から足せる構造を維持する
   - 状態遷移は `Action` 駆動のまま保つ。タッチ UI のボタン（文節移動・区切り伸縮・範囲選択）は Action を直接送る方式にする（§4.2）
6. **クロスコンパイル可能な依存に留める**
   - 新しい依存クレートは `aarch64-apple-ios` / `aarch64-linux-android` でビルドできるものを選ぶ。デスクトップ専用の依存は `server` のバイナリ側か feature の裏に置く

## 4. コア側の追加（モバイル着手時に実装）

### 4.1 組み込み API（FFI 層）

- 新 crate `core/ffi/`（仮）: C ABI で `nagi_create(config) / nagi_handle(handle, json_line) -> json_lines / nagi_set_notify_callback / nagi_destroy` を公開する
- メッセージは既存の JSON-RPC スキーマをそのまま流す（**プロトコルは一本化**。トランスポートだけが stdio か関数呼び出しかで異なる）
- バインディング生成は UniFFI を第一候補とする（Swift / Kotlin の両方を生成できるため）。typeshare の Swift 型生成との役割分担は着手時に決める
- 配布形態: iOS は XCFramework、Android は AAR（`cargo xtask` にビルドタスクを追加）
- クラッシュ隔離: 子プロセス化できないため、iOS ではコアのパニックが拡張ごと落ちる。`catch_unwind` で FFI 境界を守り、復帰時は `restore_session` 相当をフロントが呼ぶ

### 4.2 プロトコル追加（決定済み・実装済み）

仕様は設計書 §3.2、決定の経緯は `decisions.md` H-3・H-7・H-9。

| method | 種別 | 内容 |
| --- | --- | --- |
| `insert_reading` | F→C 要求 | `{session_id, reading}`。ローマ字を経由せず reading を挿入（フリック・12キー・物理かな配列）。未確定ローマ字は先に確定し、`Converting` 中は変換結果を確定してから挿入する。応答は `process_key` と同じ描画差分 |
| `perform_action` | F→C 要求 | `{session_id, action: ActionSpec}`。タッチ UI のボタンから `Action`（文節移動・区切り伸縮・範囲選択・スタイル変換等）を直接実行。キーマップは経由しない。`Insert` / `InsertText` / `CommitAndPassThrough` / `NoOp` は指定できない |
| `initialize` の `client_capabilities` | — | 任意。`memory_limit_mb`、`environment`（`set_environment` と同じ値）、`input_modality: physical_keyboard \| touch`。注入値は `sysinfo` の検出より優先 |

- キーマップ（TOML）の解決は物理キー経路のまま使う。タッチ UI のレイアウトはフロントの描画責務、ボタンと Action の対応はコアの設定（プリセット）で持つ
- 12キーのトグル入力（「あ」を連打して「い」）とフリック方向の解決は、**コアで行う**（ロジックをフロントに持ち込まない原則）。`process_key.kind` は拡張しない（H-3）。この解決を `insert_reading` の前段としてコアのどこに置くかは未実装
- 旧案にあった `platform` / `low_power` / `thermal_state` / `supports_preedit_attributes` は、電源・熱は `environment` に集約し、`platform` / `supports_preedit_attributes` は未実装
- `input_modality` は現状保持のみで、挙動には使っていない

### 4.3 環境プロファイル

- モバイルの既定は `light`（iOS は `minimal` から開始し、実測したメモリ余裕に応じて昇格）
- 低電力モード・温度上昇（`thermal_state`）で自動的に `minimal` へ降格する（§4.7 の実行時切替をそのまま使う）
- iOS はメモリ警告（`didReceiveMemoryWarning`）を受けたらフロントが通知し、コアはモデルを解放して `minimal` へ落とす

## 5. フロントエンド設計

### 5.0 アプリ仕様の参考: azooKey

モバイル版のアプリ仕様（キーボード UI・本体アプリの構成・設定項目）は azooKey（iOS）を参考にする。azooKey も「独自の変換エンジン + ニューラル変換（Zenzai）+ キーボード拡張」という Nagi と近い構成を取っているため。

- 参考にする範囲: キーボードレイアウト（フリック / ローマ字）と切替、候補バーの挙動、カーソル移動・文節調整の UI、本体アプリの構成（有効化チュートリアル・設定・ユーザー辞書・学習リセット）、フルアクセス未許可時の縮退、キーボード拡張のメモリ対策
- 参考にしない範囲: 変換エンジン本体（Nagi は Rust コアを使う。`decisions.md` F の方針どおり azooKey の変換器は組み込まない）
- Android 版も同じ仕様を Kotlin で実装し、iOS と操作感を揃える
- 具体的な挙動は Phase M0 で azooKey のソース（MIT）と実機挙動を確認して仕様表にまとめる。部分的にコードを移植する場合は出典を明記する

### 5.1 共通

- キーボード UI: QWERTY ローマ字（v1）とフリック（v1 で両方提供を目標）。レイアウトの描画はフロント
- 候補バー: キーボード上部。N-best の横スクロール + 展開で全候補
- 文節・範囲操作: 候補バーの上段に「セグメント列」を表示し、タップで注目文節、左右ドラッグで区切り伸縮、2本指/ロングプレス+ドラッグで範囲選択（Action に写像）。iOS は marked text に属性を付けられないため、このセグメント列が注目文節表示の主手段になる
- スタイル変換: 範囲選択後にアクションボタン（プリセット一覧）
- 本体アプリ: 辞書・モデルの取得、設定 GUI、学習データ削除、有効化手順の案内

### 5.2 iOS

- `UIInputViewController` + Swift（SwiftUI 可）。コアは XCFramework として拡張に同梱
- 辞書・モデルは本体アプリが取得して App Group 共有コンテナへ置く。拡張がこれを読むには `RequestsOpenAccess`（フルアクセス）が必要。フルアクセスの用途（データ参照のみ・外部送信なし）を本体アプリで明示する
- フルアクセス未許可時: ひらがな・カタカナ変換のみで動作し、許可を促す表示を出す（入力は失わない）
- メモリ上限への対応: 辞書は mmap（§3-3）、モデルは量子化版 + mmap。上限を超える端末では LLM を使わない
- 外付けキーボードの入力はキーボード拡張に届かないため、物理キーボードでの利用はサポート外（OS 標準 IME を使う）
- SideStore 配布に伴う要検証事項（Phase M0）: キーボード拡張と App Group の entitlement が SideStore の再署名で維持されるか、無料 Apple ID の制限（有効アプリ数・App ID 数）に拡張がどう数えられるか

### 5.3 Android

- `InputMethodService` + Kotlin。コアは JNI 経由（AAR）
- `setComposingText` の Span で注目文節・範囲選択を装飾できる（デスクトップ同等の表示）
- 物理キーボード（`KeyEvent`）はデスクトップと同じキー経路（keysym 正規化）で扱う
- 再変換: `InputConnection.getTextBeforeCursor` / `setComposingRegion` で確定済みテキストの再変換を実現する
- `IME_FLAG_NO_PERSONALIZED_LEARNING`（シークレットモード）とパスワード欄では学習・Surrounding Text 取得を止める

### 5.4 予測候補バーの要件（暫定・要レビュー。decisions H-11）

**暫定追記**。仕様は未確定で、実装は未着手。デスクトップの予測変換（Tab）は変更しない。

#### 現状実装の事実（2026-10-01 時点のコード）

- 入口は `Action::Predict`（Tab）のみ。`Composing` で、全 piece が `Japanese`（Literal を含むと不発）、保留ローマ字は `flush_pending` で確定させ、reading が `predict.min_chars`（既定 1、範囲 1〜20）以上のとき `ConversionBackend::predict(prefix, left_context, 50)` を呼ぶ（`engine.rs` `predict`）
- 1 件以上あれば `Converting` に遷移し、reading 全体を 1 文節として候補ウィンドウを開く。0 件なら何もしない。入力中に自動では出ない（候補は押下時の一度きりの生成で、打鍵に追従して更新されない）
- 供給元は 2 つだけ（`server/pipeline.rs` `predict`）。(1) 学習キャッシュ `Learner::lookup_prefix`（reading 前方一致、完全一致を含む。score 降順・同点は surface 昇順。文脈ハッシュ一致でボーナス。全行の線形走査）、(2) ユーザー辞書オーバーレイ `lookup_prefix`（完全一致は除外。`HashMap` 走査のため順序は不定。件数は少ない前提の線形探索）。学習 → ユーザー辞書の順に連結、surface で重複除去、上限 50 件で切る
- **システム辞書の前方一致・LLM の続き生成・Rewriter・かな候補は使わない**。`[ranking]` の順序設定も適用されない。プロファイル（`minimal` 含む）による挙動差もない（学習が有効なら `minimal` でも学習・ユーザー辞書の予測は動く。`learning_enabled` が false なら学習分は空）
- 件数: エンジン側の収集上限は 50（`CANDIDATE_LIMIT`）。表示は `candidates.page_size`（既定 9、`conversion.num_candidates`）でページ分けされるだけで、プロトコルに件数上限を指定する手段はない。`CandidatesView` は `items / selected / page_size / visible`
- `Composing`（ライブ変換含む）の描画差分に候補は載らない（preedit のみ）
- Converting 中の Space（NextCand）は通常候補を循環し、予測候補へは移らない（G-44 で現状仕様として確定済み）

#### モバイルの要件（提案）

1. **自動表示**: モバイルでは Tab 相当が無く、候補バーが常に主要 UI になる。`input_modality = touch` のとき、`Composing` 中の打鍵ごとに（Tab なしで）予測候補を生成して `candidates` に載せる。選択してもセッションの状態は `Composing` のまま（`Converting` へ遷移させない）。タップで該当候補を確定し、読み全体を置き換えて学習通知する（Mozc/azooKey の「入力中候補」に相当）
2. **予測と変換候補の関係**: 候補バーは「入力中の予測候補」と「Space 後の変換候補（N-best）」を同じ領域で切り替える。`Composing`: 予測、`Converting`: 変換候補（デスクトップと同じ）。両者は同時に出さない。ただし `Composing` の先頭にライブ変換結果（あれば）を置くかは H-11 の論点
3. **件数**: ホストが候補バーの上限を渡せるようにする（画面幅・折返し/横スクロールの別で変わるため）。コア側の既定は予測 `bar_limit` = 10 件程度。デスクトップの `page_size` とは別の概念として扱い、バーは横スクロールで全件、展開ビューで一覧という §5.1 の方針に合わせてコアは上限件数のみ守る
4. **供給元の優先順**: 学習 → ユーザー辞書 → システム辞書の前方一致 → LLM（可能なとき）。ライブ変換結果は予測の先頭候補にはしない（二重表示を避ける）。現状（学習・ユーザー辞書のみ）では、新規ユーザーの学習が空の間に候補が出ず、主要 UI として成立しない。**システム辞書の前方一致候補の追加が前提**（`Dictionary` に前方一致列挙 API が現状ない。頻度・品詞コスト順で上位を返す）
5. **`minimal` プロファイル**: 学習 + ユーザー辞書 + システム辞書の前方一致のみで動かし、LLM は使わない（モバイルの既定が `minimal`/`light` のため、これが実質の標準経路）。`light` 以上で LLM を使う場合も、同期応答には載せず遅延通知で差し替える（下記 5）
6. **レイテンシ予算**: 予測は打鍵ごとに走るため、既存の「キー入力→ひらがな反映 p95 < 16ms」を悪化させない。予測の同期部分（学習 + ユーザー辞書 + システム辞書の前方一致）は同じ応答に載せる前提で 5ms 程度を目標、超える見込みなら予測だけ遅延通知（`revision` で古いものを破棄）にしてひらがな反映を先に返す。LLM 由来は Space 変換と同様に非同期。学習の線形走査は `max_entries` 規模で打鍵ごとには重いため、読みの前方一致インデックス（ソート済み構造）化が必要になる可能性がある（要計測）
7. **読み未確定のローマ字バッファ**: 予測は確定済みの reading（かな化済み）の前方一致で生成する。保留中のローマ字（例 `k`、`n` 単独）は予測のキーに含めない（`n` は `ん` に確定させず保留のまま）。末尾が保留ローマ字だけのときは、直前までの reading で得た候補を維持し、保留文字が確定して reading が伸びた時点で更新する。デスクトップの Tab 経路が行う `flush_pending`（`n` → `ん` の強制確定）は、自動表示では行わない。フリック/12キーの `insert_reading` 経路では保留が無いので常に reading 全体が対象
8. **対象外条件**: Literal piece を含む入力は予測しない（現状どおり）。secure input / シークレットモード / パスワード欄では学習分を出さない（学習停止条件に従う）。`predict.enabled = false` でバーは変換候補のみ
9. **プロトコル拡張（提案のみ・未実装）**: (a) `initialize.client_capabilities` に `candidate_bar_limit: u32`（任意）または `set_environment` 相当の更新手段（画面回転・折りたたみ端末での幅変化に追従）。(b) 描画差分の `candidates` に予測であることを示す `kind: prediction | conversion`（現状はフロントが状態から推測するしかない）。(c) 予測候補が読みの一部だけを置き換えるか全体を置き換えるかを示すため、`CandidateView` に `reading`（その候補が対応する読み）を任意で追加。(d) 予測の遅延更新用の通知（既存の遅延通知に `kind` を足す形を第一候補）。いずれも後方互換な追加（任意フィールド）にする

#### 現状とのギャップ

| 項目 | 現状 | 要件 |
| --- | --- | --- |
| 起動 | Tab のみ（押下時に一度） | touch では打鍵ごとに自動 |
| 状態 | `Converting` へ遷移 | `Composing` のまま候補だけ載せる |
| 供給元 | 学習・ユーザー辞書 | + システム辞書前方一致（+ LLM は任意） |
| 件数指定 | 内部定数 50、表示は `page_size` | ホストから上限指定、既定は約 10 |
| `minimal` | 供給元の差は無い | 辞書系のみで常用に耐える |
| 順序の決定性 | ユーザー辞書側は不定 | 決定的な順序（登録順または頻度順） |
| ローマ字保留 | Tab 時に強制確定 | 自動時は確定させず直前の候補を維持 |
| 種別 | 無し | `prediction`/`conversion` の区別 |

## 6. 配布と更新

デスクトップと同じく、公式ストアと有料の開発者プログラムを使わない（Apple Developer Program 非加入の方針を維持）。

### 6.1 iOS: SideStore

- 未署名の `.ipa` を `shiki-01.com` と GitHub Releases で配布し、ユーザーが SideStore で自分の Apple ID で署名してインストールする
- SideStore のソース（AltStore 互換のソース JSON）を `shiki-01.com` に置き、SideStore 上で更新を配信する
- 無料 Apple ID の署名は 7 日で失効するため、SideStore の自動更新（再署名）に任せる。失効してもキーボードは OS 標準に戻るだけで入力は失われない。本体アプリで失効が近いことを表示する（方法は要検証）

### 6.2 Android: APK 直接配布

- 署名済み APK を `shiki-01.com` と GitHub Releases で配布する。署名鍵は固定し、上書き更新（データ保持）を可能にする
- Google の開発者認証要件（サイドロードアプリへの適用）の影響は着手時に確認する

### 6.3 更新確認（両 OS 共通）

更新確認は本体アプリで行う（iOS のキーボード拡張はフルアクセスなしで通信できないため、拡張からは通信しない）。ed25519 署名検証はデスクトップと同じ実装をコアから使う（§3-4）。

| 更新対象 | iOS | Android |
| --- | --- | --- |
| データ資産（辞書・モデル・プリセット・ローマ字テーブル） | 本体アプリが取得・検証して App Group に配置。**再インストール不要** | 本体アプリが取得・検証してアプリ領域に配置。**再インストール不要** |
| アプリ本体（コード） | 本体アプリが新版を通知し、SideStore の更新へ誘導（URL スキームで SideStore を開けるかは要検証）。iOS は署名済みでないコードを実行できないため、コードの更新は SideStore の再署名が必須 | 本体アプリが APK を取得・検証し、`PackageInstaller` で上書きインストール（`REQUEST_INSTALL_PACKAGES`。初回はユーザー確認が必要） |

- データ資産は「アプリ本体のバージョンとの互換範囲」をマニフェストに持ち、非互換なデータは取得しない
- 取得中・検証失敗時は旧データのまま動作を続ける（入力を失わない）
- 自動確認は無効化できる（デスクトップの `update.auto_check` と同じ扱い）

## 7. ロードマップ（案）

デスクトップ版 Phase 1〜6 の後に着手する。**Android 先行を推奨**（メモリ上限・フルアクセス・再署名の制約がなく、分離設計の検証に向くため）。

| Phase | 内容 | DoD |
| --- | --- | --- |
| M0 | 技術検証: コアの iOS/Android クロスビルド、FFI 最小実装、iOS 拡張内のメモリ実測（辞書 mmap・モデル量子化別）、端末別の推論レイテンシ、SideStore でのキーボード拡張・App Group の動作、azooKey の仕様調査 | 実測値・iOS の LLM 可否・SideStore 可否・仕様表を `decisions.md` に記録 |
| M1 | Android MVP: QWERTY ローマ字 + 文全体/文節変換 + 候補バー + セグメント列 + 更新確認（§6.3） | 自分の Android 端末で常用可能。コア側の変更は FFI 層と §4.2 のみ |
| M2 | フリック入力 + 学習・ユーザー辞書 + 範囲操作 | フリックで1週間常用 |
| M3 | iOS（SideStore 配布・更新確認を含む） | 自分の iPhone で常用可能 |
| M4 | スタイル変換・設定 GUI のモバイル対応 | デスクトップと同等の機能 |

## 8. リスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| iOS 拡張のメモリ上限で LLM が載らない | 高 | `minimal` の品質を保つ。M0 で実測し、不可なら iOS は辞書 + 学習のみ |
| フルアクセス要求によるユーザーの不信 | 中 | 用途の明示、未許可でも入力できる縮退動作、ネットワーク不使用の明記 |
| SideStore でキーボード拡張・App Group が動かない、または 7 日失効が運用負担になる | 中 | M0 で検証。失効時も OS 標準キーボードに戻るだけで入力は失われない |
| Android のサイドロード規制の強化 | 中 | 動向を確認し、必要なら開発者認証を検討 |
| タッチでの範囲操作の操作性 | 中 | セグメント列 UI を M1 で試作し、実利用で調整 |
| デスクトップ実装中に §3 の制約が破られる | 中 | レビュー観点に追加。M0 前に mobile ターゲットの `cargo check` を CI に入れることを検討 |
